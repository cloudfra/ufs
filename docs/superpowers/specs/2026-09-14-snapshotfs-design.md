# SnapshotFS — Design Spec

## Goal

Extend the existing `Snapshot(fsys FS) SnapshotFS` stub (`snapshot.go`) into a
usable feature: taking a snapshot of a writable `FS` freezes that FS (all
further `Create`/`MkdirAll`/`Remove`/`RemoveAll` calls made through it return
`fs.ErrPermission`) until the snapshot's write lock is released, and hands
the caller back a read-write `SnapshotFS` that behaves like the frozen FS but
lets them stage new writes on top of it. Staged writes can be flushed to the
frozen parent with `Sync`. `Close` releases the write lock; it never commits
staged writes — that is exclusively `Sync`'s job — so any writes never passed
to `Sync` are simply dropped when `Close` runs.

All new logic is scoped to `snapshot.go` (and its test file) with one
narrow, unavoidable exception: the freeze itself has to live on `nestFS`,
because every `FS` returned by `New()`/`CreateURI()` is a `*nestFS`
(`ufs.go`), and `nestFS` is the single choke point every write passes
through regardless of which backend is mounted underneath.

## Architecture

```text
Snapshot(fsys FS) (SnapshotFS, error)
  → type-assert fsys to *nestFS
  → parent.acquireWriteLock()        // CAS; fails if the write lock is already held
  → return &snapshotFS{parent: parent, ...}

snapshotFS (implements FS + SnapshotFS)
  reads  → in overlay?      → serve from overlay (memFS)     // overlay always wins: it reflects the latest op
         → tombstoned?      → fs.ErrNotExist
         → else             → serve from parent (frozen, safe to read directly)

  writes → Create/MkdirAll  → write into overlay, clear any tombstone, append log entry
         → Remove/RemoveAll → tombstone the path(s), best-effort remove from overlay, append log entry per deleted node

  Sync()  → apply tombstoned removals to parent, then copy overlay contents into parent,
            then clear overlay + tombstones (repeatable; GetLog() is untouched). Does not release the write lock.
  Close() → drop overlay + tombstones unconditionally (never commits — that's Sync's job only),
            release the write lock on parent
  GetLog() → cumulative log of every write made through the snapshot, across all Syncs
```

### Why the parent is always frozen, with no read-write mode underneath

The overlay only stores *deltas*; reads for anything not yet in the overlay
fall through live to the parent. This is what keeps an idle snapshot free
(no upfront copy, per the CLAUDE.md work-minimization priority). But it only
gives a correct point-in-time view if the parent cannot change out from
under it — a parent write to a path the snapshot hasn't touched would leak
straight through the merge-read logic. A copy-on-first-read alternative
(materialize a path into the overlay the first time it's read) would allow
concurrent parent writes, but costs a copy on every first read and extra
"have I already materialized this" bookkeeping. Per direction from the
design discussion, this spec keeps the always-frozen model and does not
build copy-on-first-read.

### Data flow — write then Sync

```text
snap, _ := Snapshot(fsys)          // fsys frozen
snap.Create("a/b.txt")             // written into snap's overlay only; fsys still shows old/missing a/b.txt
snap.Remove("c.txt")               // tombstoned in snap; fsys still shows c.txt
snap.Sync()                        // fsys now has a/b.txt and c.txt is gone; overlay/tombstones cleared
snap.Close()                       // fsys unfrozen (write lock released); nothing left staged to drop
```

```text
snap, _ := Snapshot(fsys)          // fsys frozen
snap.Create("a/b.txt")             // staged only
snap.Close()                       // fsys unfrozen; a/b.txt was never Sync'd, so it is dropped, not written to fsys
```

## Constraints

- No changes to the public `FS`/`WriteFS`/`ReadFS` interfaces in `ufs.go`.
- No changes to any backend (`localFS`, `memFS`, `gcsFS`, ...) — the freeze
  is enforced once, in `nestFS`.
- Must not regress existing `nestFS` behavior or its `fstest.TestFS`
  conformance suite.
- `SnapshotLogEntry` (`name`, `operation`, and a `FileAttributes metadata`
  field reusing the message added in #273) is already added to
  `proto/ufs.proto` in a separate PR and regenerated by `make protos`; this
  spec does not change the proto further.
- Only one write lock may be held on a given `*nestFS` at a time; a second
  `Snapshot()` call on the same parent fails until the first is closed.

## Changes

### `nestfs.go` — the write lock

```go
type nestFS struct {
    fsys      FS
    ctx       context.Context
    mounts    *mountMap
    args      FSArgs
    writeLock atomic.Bool   // new
}

func (fsys *nestFS) acquireWriteLock() bool {
    return fsys.writeLock.CompareAndSwap(false, true)
}

func (fsys *nestFS) releaseWriteLock() {
    fsys.writeLock.Store(false)
}

func (fsys *nestFS) checkWriteLock(op, name string) error {
    if fsys.writeLock.Load() {
        return pathError(op, name, fs.ErrPermission)
    }
    return nil
}
```

`Create`, `MkdirAll`, `Remove`, `RemoveAll` each call `fsys.checkWriteLock(op,
name)` immediately after their existing `fsys.validPath(op, name)` call,
returning the error if non-nil — the same shape `readOnlyFS` already uses
for its permission errors.

Scoping note (matches `readOnlyFS`'s existing scope): the write lock is
checked on whichever `*nestFS` value the caller writes through. A nested
mount's own `*nestFS`, if obtained and used independently of the frozen
top-level handle, is not separately frozen. This is an existing, accepted
limitation of the wrapper pattern in this codebase, not new to snapshots.

#### Invalidating already-open write handles

A `File` obtained from `fsys.Create` *before* a snapshot freezes `fsys` must
stop accepting writes once the freeze takes effect — otherwise the freeze
would be trivially bypassable by any caller already holding a handle. This
needs no handle registry: `nestFS.Create` wraps the `File` it returns in a
small decorator that closes over `&fsys.writeLock` (the same flag
`checkWriteLock` reads) and checks it on every `Write`, `WriteAt`, and
`WriteString` call, ahead of delegating to the real file:

```go
// lockGatedFile makes Write/WriteAt/WriteString fail once writeLock is set,
// so a File obtained before a snapshot freezes its nestFS stops accepting
// writes without needing a registry of open handles.
type lockGatedFile struct {
    File
    writeLock *atomic.Bool
    stale     atomic.Bool // sticky: once tripped, invalid for the rest of this handle's life
}

func (f *lockGatedFile) checkStale() error {
    if f.stale.Load() {
        return fs.ErrPermission
    }
    if f.writeLock.Load() {
        f.stale.Store(true)
        return fs.ErrPermission
    }
    return nil
}

func (f *lockGatedFile) Write(p []byte) (int, error) {
    if err := f.checkStale(); err != nil {
        return 0, err
    }
    return f.File.Write(p)
}

func (f *lockGatedFile) WriteAt(p []byte, off int64) (int, error) {
    if err := f.checkStale(); err != nil {
        return 0, err
    }
    return f.File.WriteAt(p, off)
}

func (f *lockGatedFile) WriteString(s string) (int, error) {
    if err := f.checkStale(); err != nil {
        return 0, err
    }
    return f.File.WriteString(s)
}
```

`nestFS.Create` wraps its return value: `wrapFile(f, false,
mountFS.args.BufMode)` becomes `&lockGatedFile{File: wrapped, writeLock:
&fsys.writeLock}` (`fsys`, the receiver the caller called `Create` on — the
handle a snapshot actually locks — not `mountFS`, the possibly-different
nested `*nestFS` the path resolved to). `Read`/`ReadAt`/`Seek`/`Close` are
untouched: a snapshot only forbids writes, so a handle opened before the
freeze can still be read from and closed normally.

Invalidation is sticky (the `stale` flag, not a live re-check) so that a
handle that raced a `Write` against an active freeze stays invalid even
after the snapshot later releases the write lock — the parent's content
may have been replaced out from under that handle by `Sync` in the
meantime (e.g. via `Create`+truncate on backends where that reuses or
replaces the underlying inode), so silently letting writes resume post-lock
could write into a now-stale or orphaned file. A handle that saw the lock
clear without ever attempting a write while it was held is never marked
stale and keeps working normally.

### `snapshot.go` — full rewrite

```go
type SnapshotFS interface {
    FS

    // Sync copies all staged writes into the parent FS and applies all
    // staged removals to it. It may be called multiple times; a Sync with
    // nothing staged is a no-op. It does not release the write lock.
    Sync() error

    // Close drops any staged writes and removals that were never passed to
    // Sync, without applying them, and releases the write lock on the
    // parent FS. Close never commits anything — that is exclusively Sync's
    // job. Close is idempotent; calling it again is a no-op.
    Close() error

    // GetLog returns the cumulative log of every write made through the
    // snapshot (via Create, MkdirAll, Remove, RemoveAll), across all Syncs,
    // in the order they were made.
    GetLog() []*pb.SnapshotLogEntry
}

type snapshotFS struct {
    parent *nestFS

    mu         sync.Mutex
    overlay    FS                  // lazily created memFS; nil until first write
    tombstones map[string]struct{} // fs.ValidPath-form paths removed but not yet synced
    log        []*pb.SnapshotLogEntry
    closed     bool
}
```

`Snapshot(fsys FS) (SnapshotFS, error)`:

1. Type-assert `fsys` to `*nestFS`; return a descriptive error if it isn't
   one (mirrors the existing `ReadOnly`/`FaultInjector` pattern of working
   against the library's own types).
2. Call `parent.acquireWriteLock()`; return an error if it's already held.
3. Return a `*snapshotFS` wrapping `parent`.

Read methods (`Open`, `Stat`, `Lstat`, `ReadFile`, `ReadLink`, `ReadDir`,
`Glob`): under `fsys.mu`, check the overlay (if non-nil) first → serve from
there if present; else check tombstones (exact path, or an ancestor
directory tombstoned by `RemoveAll`) → `fs.ErrNotExist`; else serve from
`parent`. The overlay is checked first specifically so that re-creating a
path underneath a `RemoveAll`-tombstoned directory (e.g. `RemoveAll("dir")`
then `Create("dir/new.txt")`) makes `dir/new.txt` visible again, even
though `dir` itself is still tombstoned. `ReadDir`/`Glob` union parent
entries (minus tombstoned names) with overlay entries for that directory,
overlay winning on name collisions.

Write methods:

- `Create(name)` / `MkdirAll(name, perm)`: lazily create the overlay
  (`memFS`) on first use, create any needed parent directories in the
  overlay, clear a tombstone on `name` if present, delegate to the overlay,
  append a log entry (`operation` = `"create"` / `"mkdir"`, `metadata` =
  the resulting node's `FileAttributes`, built from the overlay's
  post-write `Stat`).
- `Remove(name)`: `Stat` `name` against the merged snapshot view *before*
  mutating anything, so `metadata` captures the node as it existed at
  removal time; add `name` to `tombstones`, best-effort remove it from the
  overlay if present (ignore `fs.ErrNotExist`), append one log entry
  (`operation` = `"remove"`). If the pre-removal `Stat` fails (`name` never
  existed), `metadata` is left absent rather than failing the removal.
- `RemoveAll(name)`: walk the merged snapshot view rooted at `name` first
  (via `fs.WalkDir(fsys, name, ...)`, so the walk itself sees the
  overlay+tombstone+parent merge like any other read), collecting every
  node under it (files and directories, `name` included). For each node
  encountered, capture its `FileAttributes` from the walk's `DirEntry.Info`
  and append one log entry (`operation` = `"removeall"`) — so a `RemoveAll`
  on a directory with descendants produces one log entry per deleted node,
  not just one for the root. This is an intentional O(subtree size) cost
  (both the walk and the resulting log entries), accepted so `GetLog()` is a
  complete record of every file a `RemoveAll` deleted. After the walk (or
  immediately, if `fs.WalkDir` reports `name` doesn't exist — a no-op, per
  `ufs.go`), mark `name` as a prefix tombstone in `tombstones` and
  best-effort remove it from the overlay if present.

All methods — read and write — return `pathError(op, name, fs.ErrClosed)`
if `closed` is true, rather than silently falling through to `parent`
(which may no longer even be frozen by this snapshot at that point).

`Sync()`: under `fsys.mu`, applies tombstoned removals to `parent`
**before** copying the overlay, so that a path resurrected in the overlay
underneath a tombstoned ancestor directory (e.g. `RemoveAll("dir")` then
`Create("dir/new.txt")`) survives the sync instead of being deleted by its
ancestor's removal:

1. For each tombstoned path, call `parent.RemoveAll` (paths tombstoned via
   `RemoveAll`) or `parent.Remove` (paths tombstoned via `Remove`),
   treating `fs.ErrNotExist` as success (the path may already be gone from
   the parent, or this may be a retried `Sync` after a prior partial
   failure).
2. If the overlay is non-nil, walk it with `ForEachFilename` and, for each
   file, `parent.MkdirAll` its directory then `Copy(overlay, name, parent,
   name)` (reusing `op.go`'s existing helpers).

On success, discard the overlay (drop the reference; the next write
recreates it) and clear `tombstones`. `log` is never touched by `Sync`.

`Close()`: under `fsys.mu`, if already `closed`, return `nil` (idempotent);
otherwise drop the overlay and clear `tombstones` unconditionally — without
ever calling anything Sync-like — then `parent.releaseWriteLock()` and set
`closed = true`. `Close` never fails because of staged, unsynced changes; it
simply discards them. Callers who want staged writes to persist must call
`Sync()` themselves before `Close()`.

## Testing

New `snapshot_test.go`:

- `Snapshot` on a memory-backed `FS`: parent `Create`/`MkdirAll`/`Remove`/
  `RemoveAll` all return `fs.ErrPermission` while the write lock is held.
- A `File` opened via `parent.Create` *before* `Snapshot()` is called: once
  the write lock is acquired, `Write`/`WriteAt`/`WriteString` on that
  already-open handle all return `fs.ErrPermission`, while `Read`/`Seek`/
  `Close` on it keep working. The handle stays write-invalid even after the
  snapshot is later closed (sticky invalidation) if a write was attempted
  while the lock was held; a handle that never attempted a write during the
  freeze is unaffected once the lock clears.
- Read-your-writes: `snap.Create` then `snap.Open`/`snap.ReadFile` see the
  new content; parent is unaffected until `Sync`.
- `snap.Remove` on a file that exists only in the parent hides it from
  `snap.Open`/`snap.ReadDir` before `Sync`, and actually removes it from the
  parent after `Sync`.
- `RemoveAll` on a directory hides the whole subtree from the snapshot's
  merged `ReadDir` before `Sync`, and removes it from the parent after.
- `RemoveAll` on a directory followed by `Create` of a file underneath it
  (before `Sync`): the new file is visible through the snapshot immediately
  (overlay wins over the ancestor tombstone), and after `Sync` the parent
  has exactly that one file under the directory — its removed siblings do
  not reappear and the new file is not deleted by the directory removal.
- `RemoveAll` on a directory containing several files and a nested
  subdirectory produces one `GetLog()` entry per deleted node (the root, the
  subdirectory, and every file), each with `metadata` matching that node's
  pre-removal state.
- `Sync` is repeatable: call it twice in a row with nothing staged between
  is a no-op and returns nil both times.
- Interleaved `Sync` calls: stage a write, `Sync`, stage another write,
  `Sync` again — parent ends up with both.
- `Close` after staging writes with no `Sync`: the parent never receives
  those writes, and the write lock is released.
- `Close` after `Sync`: releases the write lock; nothing left to drop.
- `Close` is idempotent: calling it twice returns nil both times and does
  not panic or double-release the write lock.
- A second `Snapshot()` call on the same parent, while the first snapshot's
  write lock is held, returns an error; succeeds once the first is closed.
- `GetLog()` reflects every write made through the snapshot, across
  multiple `Sync` calls, in order.
- Each log entry's `metadata` reflects the node's state at the time of the
  operation: a `Create`/`MkdirAll` entry's metadata matches the new node;
  a `Remove`/`RemoveAll` entry's metadata matches the node as it existed
  immediately before removal (verified by comparing against a `Stat` taken
  just before the call in the test).
- `Snapshot()` on an `FS` that is not a `*nestFS` (if constructible in a
  test) returns a descriptive error rather than panicking.
- Concurrent writers to the same `snapshotFS` from multiple goroutines don't
  race (run under `go test -race`, per `make test`).

## Known limitations

- **No concurrent read-write access to the parent while a snapshot is
  held.** This is intentional, not a gap — see "Why the parent is always
  frozen" above. A future copy-on-first-read mode could relax this if a
  concrete use case needs it, but it is out of scope here.
- **Already-open write handles obtained through the snapshotted `*nestFS`
  are invalidated for writes, but handles obtained any other way are not.**
  `lockGatedFile` (see "Invalidating already-open write handles" above)
  only wraps files returned by that specific `*nestFS`'s `Create`. A raw
  file handle opened directly against the backend outside of `ufs`
  entirely (e.g. `os.OpenFile` on a `localFS`'s underlying directory) is
  invisible to the library and cannot be invalidated. This mirrors the same
  scoping limit as the write lock itself.
- **A nested mount's own `*nestFS`, if held and used independently of the
  top-level handle that was snapshotted, is not frozen.** Matches the
  existing scoping of `readOnlyFS`/`FaultInjector`; not new to snapshots.
- **Not atomic across the whole `Sync`.** If an error occurs partway
  through applying staged writes/removals to the parent, the parent may
  end up partially updated (same caveat `op.go`'s `Rsync` already
  documents). The overlay/tombstones for the parts that did apply are not
  cleared in that case, so a retried `Sync` will attempt the remainder;
  this is safe because removals treat `fs.ErrNotExist` as success and
  copies simply overwrite.
- **`RemoveAll` on a large subtree costs a full walk and one log entry per
  node**, both to build the complete `GetLog()` record. Callers removing
  very large trees through a snapshot should expect `RemoveAll`'s cost (and
  the snapshot's log memory) to scale with subtree size, not be O(1) as
  bare `RemoveAll` on most backends is.
